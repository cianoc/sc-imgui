## Overview

This directory is the only Lisp code that crosses into C. It loads the native library built in `native/` (`libsc_imgui_shim`) and binds its functions with CFFI. Everything else in sc-imgui reaches ImGui, ImPlot, and the shim through the packages defined here.

| Package | Contents |
| --- | --- |
| `%imgui` | Dear ImGui, through cimgui: functions, structs, and enum constants. Generated. |
| `%implot` | ImPlot, through cimplot. Generated. |
| `%shim` | The shim's own functions from `native/shim.h`: window, frames, fonts, background colour, headless mode, assertions. Hand-written. |
| `sc-imgui.bindings` | Library loading and the `optional-string` type. Hand-written. |

The `%` prefix marks them as low level: they mirror the C APIs one-to-one and check nothing. Application code should use `gui` (`src/gui/README.md`), dropping into these only for something `gui` doesn't wrap yet.

It's a separate ASDF system, `sc-imgui/bindings`, depending on `cffi`, `cffi-libffi`, `alexandria`, and `uiop`. The generator and tests can load it without the rest of sc-imgui. Files load in this order:

1. `package.lisp`: all four packages.
2. `types.lisp`: `optional-string`. **Must come before the generated files**, which use it in every string argument.
3. `library.lisp`: finds and loads the native library. Must come before any binding is called.
4. `shim.lisp`: the `%shim` functions.
5. `imgui.lisp`, then `implot.lisp`: the generated bindings. `implot.lisp` uses structs defined in `imgui.lisp`.

## Generated versus hand-written files

| File | Kind | Edit it? |
| --- | --- | --- |
| `imgui.lisp` (~14,000 lines) | **Generated** by `make bindings` from cimgui's JSON | **Never.** Change the generator, then regenerate. |
| `implot.lisp` (~5,500 lines) | **Generated** from cimplot's JSON | **Never.** |
| `package.lisp` | Hand-written | Yes |
| `types.lisp` | Hand-written | Yes, with care: it relies on CFFI internals |
| `library.lisp` | Hand-written | Yes |
| `shim.lisp` | Hand-written, mirrors `native/shim.h` | Only together with `shim.h` |

Generated files start with this header, naming the submodule commit they came from:

```lisp
;;; GENERATED by generator/main.lisp; do not edit.
;;; cimgui commit: 5d7cc7e12de9a868bbecc00ce2ed74e58d266f1c
```

Every `make bindings` rewrites them completely, so a hand edit is lost. They're committed so that loading sc-imgui never needs the generator or the JSON. How they're produced is in `generator/README.md`.

### The hand-written files

**`package.lisp`** — Defines `sc-imgui.bindings` (uses `CL`, exports the loading API and `optional-string`), `%shim` (uses nothing, exports its 20 functions), and `%imgui` and `%implot` (use nothing, export nothing here; the generated files export their own names).

**`types.lisp`** — Defines `optional-string`, the type every generated `const char*` argument uses. It behaves like CFFI's `:string` (a Lisp string is copied to foreign memory for the call and freed afterwards; a foreign pointer passes through), except that `nil` passes NULL, which many optional ImGui arguments need. It subclasses CFFI's own string type rather than defining a new one, because calls that pass a struct by value go through cffi-libffi, which only knows how to translate CFFI's string type. Inheriting it keeps strings handled the same way on both call paths. Return values stay plain `:string`.

**`library.lisp`** — Works out the library's file name per platform (`libsc_imgui_shim.dylib`, `.so`, or `sc_imgui_shim.dll`), searches `*library-search-paths*` for it, and loads it, all when the file is loaded. If it isn't found, signals `shim-library-not-found` listing every path tried.

**`shim.lisp`** — One `cffi:defcfun` per function in `native/shim.h`, with comments on which thread may call each.

## How the generated API behaves

In brief; `generator/README.md` has the full rules.

- **Names:** C names lose their prefix and become hyphenated lowercase: `igBeginChild_Str` → `begin-child-str`, `ImGuiWindowFlags_NoTitleBar` → `+window-flags-no-title-bar+`. Overload suffixes like `_Str`, `_Vec2`, `_Nil` stay in the name.
- **`bool`:** a function with a C `bool` argument or result has two definitions: `NAME-raw`, the real foreign function using `:uint8`, and `NAME`, an exported wrapper taking and returning `t`/`nil`.
- **Strings:** every `const char*` argument is an `optional-string`, accepting a Lisp string, a foreign pointer, or `nil` for NULL. String results are Lisp strings.
- **Structs by value** go in and come out as plists of slot names and values: `(list '%imgui::x 1.0f0 '%imgui::y 2.0f0)`. These calls go through cffi-libffi.
- **Structs by pointer** are foreign pointers; read their slots with `cffi:foreign-slot-value`.
- **Constants** are `defconstant`s.
- **Not bound at all:** variadic functions such as `igText` and `igSetTooltip`, templated functions, and functions with types the generator can't map.

## Gotchas when using the bindings

### Loading the system loads the native library

`library.lisp` calls `load-shim-library` when it's loaded. Without a built library, `(ql:quickload :sc-imgui)` fails with `shim-library-not-found`, as do the tests and anything else that loads `sc-imgui/bindings`. Run `make native` first.

### The search path is fixed when the file loads

`*library-search-paths*` is a `defvar`, computed from `SC_IMGUI_LIB` the first time `library.lisp` loads. Setting the environment variable later has no effect, and neither does reloading the file. To use a different directory in a running Lisp, set `*library-search-paths*` and call `load-shim-library` before anything else has loaded the library, or restart Lisp.

### A loaded library is never reloaded

Once loaded, the library stays. Rebuilding it with `make native` doesn't affect a running Lisp, and calling `load-shim-library` again does nothing. Restart Lisp to use a new build.

### Saved images remember the library's path

The library is registered by its absolute path. A core saved with `save-lisp-and-die` reloads it from that same path when it starts, so the path must still exist on the machine running the core.

### Only string arguments accept `nil`

`optional-string` turns `nil` into NULL, but other pointer arguments don't. `(%imgui:begin "w" nil 0)` is an error; write `(cffi:null-pointer)` for `p-open` and similar.

### By-value structs are plists with unexported keys

Arguments like `ImVec2` must be plists keyed by `%imgui::x`, `%imgui::y`, and so on; a missing or misspelled key is an error at call time. Returned structs are plists too: `(getf (%imgui:get-mouse-pos) '%imgui::x)`. `gui::vec2` builds one, and `gui` hides this everywhere it wraps a call.

### Call the wrapper, not `-raw`

For a function with `bool` arguments or results, the exported name is the wrapper. The `-raw` function takes and returns integers, isn't exported, and exists only because C `bool` is one byte while CFFI's `:bool` is the size of an `int`.

### Some overload names don't follow the pattern

Names come from cimgui's C names, which aren't always regular. ImPlot's double-precision overloads, for example, are `plot-line-double-ptrdouble-ptr` and `plot-scatter-double-ptrdouble-ptr`, while the single-precision ones are `plot-line-float-ptr-float-ptr`. Look a name up in the generated file rather than guessing.

### Nothing is checked

A wrong argument type, an unbalanced begin/end pair, a call outside a frame, or a call from the wrong thread is ImGui misuse. It's recorded as an ImGui assertion (check `(%shim:assert-count)` and `(%shim:last-assert)`) or crashes inside C. It isn't a Lisp error, so the runtime's per-panel error handling can't catch it.

### Thread rules

Every function here must run on the GUI thread, except `%shim:wake` and `%shim:test-request-close`. ImGui and ImPlot functions must also run inside a frame, which in practice means inside a panel.

### String arguments allocate

Each call copies every Lisp string argument into foreign memory and frees it afterwards. That's cheap for a few labels per frame, but it isn't free.

### The `%` packages don't use `CL`

`%imgui`, `%implot`, and `%shim` use no other package, so names like `%imgui:end` or `%imgui::size` never clash with Lisp symbols. It's also why the generated files print `common-lisp:defconstant` and similar in full. Don't `:use` these packages in your own code: their names would shadow standard ones.

## Maintenance when upgrading third-party libraries

### ImGui with cimgui, ImPlot with cimplot

Follow "Upgrading the third-party libraries" in `native/README.md` and "When the cimgui or cimplot pins move" in `generator/README.md`. Specific to the bindings:

1. **Regenerate** with `make bindings`, then **check the public API.** Every name listed in [Public API](#public-api-whats-used-outside-this-directory) must still exist with the same arguments. This finds any that disappeared:

    ```sh
    for n in $(grep -ohr --include='*.lisp' '%imgui:[a-z0-9+*-]*\|%implot:[a-z0-9+*-]*' src/gui src/runtime tests examples | sort -u); do
      pkg=${n%%:*}; name=${n#*:}
      file=src/bindings/$( [ "$pkg" = "%imgui" ] && echo imgui || echo implot ).lisp
      grep -qE "[ (]$(printf '%s' "$name" | sed 's/[+*]/\\&/g')[ )]" "$file" || echo "missing: $n"
    done
    ```

2. **Read the diff** of the generated files for changed argument lists of the functions you use. A changed signature still loads, then fails or misbehaves when called.
3. **Restart Lisp** before loading the new bindings. Constants are `defconstant`s, so loading a file with a changed value into a Lisp that has the old one signals a redefinition error.
4. **Run `make native`, `make test`, and `make smoke`.** The `bindings` suite runs first in the triage order in `tests/README.md`.

### Upgrade gotchas

**Overload suffixes change.** When ImGui adds an overload, a function gains a suffix and its Lisp name changes (`get-io` became `get-io-nil`). These renames are the most common breakage; look for them first.

**A function can gain or lose a `bool`.** If its signature changes to add or remove a `bool` argument or result, it switches between a plain `defcfun` and a wrapper with `-raw`. Callers using the exported name are unaffected unless the argument list changed.

**Structs that other code reads or builds must stay complete, with the same field names.** If the generator makes one opaque or a field is renamed, the code using it breaks:

| Struct | Why it matters |
| --- | --- |
| `im-vec2`, `im-vec4` | Every by-value position, size, and color |
| `im-gui-error-recovery-state` | The runtime allocates one per panel call. If it became opaque, it would have no size, and the runtime couldn't allocate it. |
| `im-gui-io`, `im-draw-list`, `im-vector-im-draw-vert` | Read by the tests |
| `im-plot-spec` | Built in full by `gui/plots.lisp`; see below |

**`ImPlotSpec` is the most fragile.** `plot-spec` in `gui/plots.lisp` builds a plist with every field of `ImPlotSpec`, with ImPlot's default values. If an ImPlot upgrade adds, removes, renames, or reorders the meaning of a field, update `plot-spec` to match the new struct and ImPlot's new defaults. Otherwise every plot call fails or draws wrongly. Compare the regenerated `(cffi:defcstruct im-plot-spec ...)` with the plist field by field.

**Constants can change value.** ImGui sometimes renumbers enums. Code using the constant names is unaffected, but saved numbers (for example, flags stored as integers) are not.

**GLFW upgrades** don't touch these files. `shim.lisp` must still match `native/shim.h`, which a GLFW upgrade shouldn't change.

### CFFI and cffi-libffi upgrades

Two hand-written files rely on CFFI internals, which can change without notice:

- `types.lisp` subclasses `cffi::foreign-string-type` and relies on cffi-libffi translating that type's arguments for by-value calls.
- `library.lisp` handles `cffi::foreign-library-undefined-error` to check whether the library is already loaded.

After upgrading CFFI or cffi-libffi through Quicklisp, run `make test SUITE=bindings`. Its string and boolean tests (`nil-string-argument`, `string-arguments-with-struct-by-value`, `bool-arguments-with-struct-by-value`, `bool-argument-plain-call`) cover both call paths, and `library-loads` covers loading.

## Maintenance of the hand-written files

### `shim.lisp` must match `native/shim.h` exactly

There's no generator for the shim and no automatic check. Each `defcfun` must match its C declaration: argument count, argument types, and return type. A mismatch is undefined behavior in C, not a Lisp error: it can pass garbage, crash, or seem to work. Always change `shim.h` and `shim.lisp` in the same commit, export new names in `package.lisp`, and follow "Adding a new shim function" in `native/README.md`.

| C type in `shim.h` | CFFI type here |
| --- | --- |
| `int` | `:int` |
| `double` | `:double` |
| `float` | `:float` |
| `void` | `:void` |
| `const char *` argument | `sc-imgui.bindings:optional-string` |
| `const char *` result | `:string` |

### Adding hand-written bindings for ImGui or ImPlot

For something the generator can't produce, such as a variadic function called with a fixed format, write the `defcfun` in its own new file, never in a generated one. Load it after `imgui.lisp` and `implot.lisp` in `sc-imgui.asd`, and export its names. Use the same conventions as the generated code (`optional-string`, `:uint8` for `bool`), and add a test to the `bindings` suite.

### Changing `optional-string`

The generator writes `sc-imgui.bindings:optional-string` into every generated function with a string argument. Renaming or moving it means changing the generator and regenerating.
